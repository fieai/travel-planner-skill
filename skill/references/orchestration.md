# Orchestration Reference

主 skill 在 5 个断点之间穿插 4 类调研子任务。本文件给出每个子任务的 prompt 模板与 fallback 策略。

## 能力探测（每次开工前）

主流程开始前先做一次能力探测，决定路径：

```
能力 = {
  ask: <能否调用 AskUserQuestion>,
  agent: <能否调用 Agent / Task 工具>,
  webaccess: <能否触发 web-access skill>,
  network: "global" | "cn-only" | "global-only" | "offline"
}
```

- `ask = false` → 用编号文本选项追问（“请回答 1A/1B/1C”）
- `agent = false` → 子任务全部串行执行，不要假装并行
- `webaccess = false` → 直接用 WebSearch + WebFetch + curl 兜底，并向用户声明“缺少 CDP，机票/小红书等反爬严格的数据可能不准”
- `network = cn-only` → 切到“国内模式”，所有子 agent prompt 用国内替代源（见下文）
- `network = offline` → 立刻告诉用户停止流程，不要硬撑

不要假定任何工具可用。即便此前刚用过，也建议每次新会话重检一次。

### 网络探测脚本

第一个子任务前跑一次（结果在本次会话复用）：

```bash
# 海外可达性
curl -s -o /dev/null -w "%{http_code}" -m 5 https://www.google.com/generate_204
# 国内可达性
curl -s -o /dev/null -w "%{http_code}" -m 5 https://www.baidu.com/
```

返回值映射：

| 海外 | 国内 | network |
|------|------|---------|
| 204 | 200 | global |
| 非 204 / 超时 | 200 | cn-only |
| 204 | 非 200 | global-only |
| 都失败 | 都失败 | offline |

切到 `cn-only` 时，主流程必须用 AskUserQuestion 让用户确认：“接受降级 / 切网后重试”。

## 子 agent prompt 写法守则

**目标导向，不指定步骤**。子 agent 自己加载 web-access skill，不需要主流程把 web-access 内容塞进 prompt。

每个子 agent prompt 必须包含：

1. **目标声明**：要拿到什么、用来做什么
2. **强一手要求**：列出该领域的一手来源（见 `data-sources.md`）
3. **必须加载 web-access skill 并遵循其指引**
4. **结构化返回要求**：明确字段名（用 Markdown 或 YAML），便于主流程聚合
5. **不确定怎么处理**：拿不到就标 `unknown` 并附查询尝试，不要猜

**避免暗示具体抓取手段**：用“获取/调研/了解”，避免“搜索/抓取/爬取”——这些词会把子 agent 锚到 WebSearch，而部分平台需要 CDP。

## 子任务模板

### 1. 签证 / 入境调研

**何时跑**：出境行程，A 断点之后、B 之前。国内行程跳过。

**Prompt 模板**：

```
调研：{出发地国籍 默认中国大陆普通护照} 持有者前往 {目的地国家} 在 {YYYY-MM-DD} 至 {YYYY-MM-DD} 期间的入境政策。

必须加载 web-access skill 并遵循其指引。

一手来源优先级：
1. 中国领事服务网（cs.mfa.gov.cn）的对应国家页面
2. 目的地国驻华大使馆 / 领事馆官网
3. 目的地国移民局 / 边境管理局官网

二手来源（携程/飞猪签证频道、攻略文）只能用于交叉验证，不能作为唯一依据。

**如果 network = cn-only**：把 #2 #3 替换为携程签证频道（`https://huodong.ctrip.com/visa/`）+ 飞猪签证（`https://lvyou.fliggy.com/visa/`）作为补充，但仍以中国领事服务网为基线。返回结果中明确标注“政策摘要来自国内 OTA，发布日期可能滞后”。

返回结构（Markdown）：
- 是否需要签证：是/否/电子签/落地签/过境签/免签
- 免签或落地签停留期：N 天
- 标准受理时长：X 个工作日
- 必备材料：列出
- 当前是否有特殊政策（疫情、临时管制、最新通告）
- 信息来源 URL（至少 2 个）
- 信息发布日期（很重要 — 旧通告可能已失效）

如果发布日期 > 6 个月前，明确标注“可能过期，需出发前复核”。
```

### 2. 目的地速览

**何时跑**：A 之后、B 之前，与签证子任务**并行**。

**Prompt 模板**：

```
调研：{目的地} 在 {YYYY-MM-DD} 至 {YYYY-MM-DD} 期间的实用旅行信息。

必须加载 web-access skill 并遵循其指引。

获取以下字段：

1. 天气
   - 优先使用 Open-Meteo API：https://api.open-meteo.com/v1/forecast?latitude=...&longitude=...&daily=temperature_2m_max,temperature_2m_min,precipitation_sum&timezone=auto
   - 给出每日高低温、降水概率、穿衣建议
   - 如该日期超出 16 天预报范围，给历史同期均值并标注

2. 治安
   - 中国领事服务网“安全提醒”最新一条
   - 目的地国如有官方治安评级（如美国 State Dept Travel Advisory）一并给出
   - 用一句话归纳：可放心 / 注意财物 / 部分区域避免 / 不建议前往

3. 货币与汇率
   - 当前对人民币汇率（精确到查询时刻）
   - 现金还是刷卡为主、支付宝/微信支付覆盖度

4. 插头与电压
   - 标准（A/B/C/D/G/I 等）+ 电压 + 频率
   - 是否需要转换器（中国常见插头能否直接用）

5. SIM / 网络
   - 目的地常用运营商
   - 推荐方案：本地 SIM / eSIM / 漫游 / 随身 WiFi 哪个划算
   - 中国移动/联通/电信境外漫游费率作为对照

6. 紧急联系
   - 目的地报警/急救号码
   - 中国驻当地大使馆/领事馆电话
   - **常用药品建议**：根据目的地气候/水质/常见疾病给清单（清迈雨季 → 蚊虫驱避剂、止泻药；东南亚 → 水土不服止泻药；高海拔 → 高反药 / 红景天；冬季滑雪 → 烫伤药、冻疮膏）
   - **当地医院推荐**：1-2 家国际部 / 私立医院（带英文/中文服务），含地址 + 电话
   - **急救用语**：5-10 句最关键的当地语言短句（"我需要医生 / 我对 X 过敏 / 救护车 / 这里痛"），中英对照表

返回结构化 Markdown，每个字段一段，附来源 URL。控制在 800 字内。
```

### 3. 景点候选池

**何时跑**：C 断点之前。

**Prompt 模板**：

```
为 {目的地} 调研景点候选池。

输入约束：
- 出行风格：{深度文化/打卡/自然/美食/主题}
- **节奏强度**：{特种兵/紧凑/标准/度假/休养}（影响候选数量与体力门槛）
- 出行人员：{成人 X、儿童 Y 岁、老人 Z 岁}
- 日期范围：{YYYY-MM-DD ~ YYYY-MM-DD}
- 必去：{用户列出}
- 忌讳：{用户列出}

必须加载 web-access skill 并遵循其指引。

按区域 / 主题分组，每组给 5-10 个候选，每个候选含：
- 名称（中文 + 当地语言原名）
- 区域 / 离市中心距离
- 主题标签（自然/人文/亲子/购物/夜景/美食）
- 开放时间（包括是否周X 闭馆、季节性闭馆）
- 票价（人民币换算）
- 平均游玩时长
- 一手来源 URL（景点官网优先）
- **点评/攻略链接（强制带）**：
  - 国内目的地：大众点评搜索 `https://www.dianping.com/search/keyword/{cityCode}/0_{景点名 URLEncode}`
  - 海外目的地：Google Reviews `https://www.google.com/maps/search/{景点名+目的地+reviews}`
  - **小红书搜索（必带，中文用户最依赖）**：`https://www.xiaohongshu.com/search_result?keyword={景点名 URLEncode}`
- 一句话亮点（不要堆形容词，写具体的）
- 风险/注意（高反、需预约、儿童/老人是否合适）

允许补充“小红书避坑提示”作为正文，但必须用 ⚠️ 标注为二手参考。

不要在这一步排日程，只出候选池。日程编排是主流程的工作。

**节奏强度对候选数的影响**（候选池要为后续的强度选择留够冗余）：

- 特种兵 → 每个区域多给 50% 候选，主流程要排满
- 紧凑/标准 → 标准数量
- 度假/休养 → 重点标注“可省略”“适合躺平”的项目，方便主流程做减法
```

### 4. 餐饮候选池

**何时跑**：D 断点用户给出口味偏好后。

**Prompt 模板**：

```
为 {目的地} 调研餐厅候选池。

输入：
- 出行规模：{N 大 + M 小（孩子年龄）}
- 口味偏好：{用户给的；如"不吃辣 / 全素 / 清淡 / 海鲜过敏"等}
- 想试的菜：{用户主动提的；没提就按目的地代表菜系覆盖}
- 节奏：{特种兵/标准/度假/...}
- 已订酒店：{酒店名 + 区域}

必须加载 web-access skill 并遵循其指引。

按场景分组（重要！每个场景独立给）：

A. 酒店附近步行可达（500m-1.5km，不打车就能吃）
   - 至少 3-4 家：本地名菜 + 简餐 + 异国 + 适合带娃各 1
   - 注意酒店所在区域的实际餐饮密度

B. 各日景点顺路
   - 按用户的每日骨架，给每天午餐/晚餐 1-2 个候选
   - 重点写"是否在景点出口/路上，不绕路"

C. 夜市 / 街边小吃
   - 当地最有名的 1-2 个夜市
   - 夜市内具体推荐摊位（米其林必比登、本地排队店）

D. 雨天兜底（室内 / 商场 / 不远不绕路）
   - 商场美食广场、地下餐饮街、连锁可靠选项

E. 用户主动要的特色（米其林 / 必比登 / 当地传奇老店等）
   - 如用户没主动要，**不要默认安排**

每个候选给：
- 中文名 + 当地语言原名
- 区域 / 离酒店或景点距离
- 菜系 / 招牌菜（具体写菜名，别"很地道"这种词）
- 人均（人民币换算，明确餐 vs 全套）
- 预约难度（即去 / 排队 1h / 必预约 / 提前 N 天）
- 是否带娃友好（高椅、儿童菜单、噪音）
- 营业时间（特别注意：很多名店有"卖完关门"，要写清）
- 一手来源 URL：官网 / 官方 IG / 大众点评（国内）/ Tabelog（日本）
- 用户体验补充：小红书 / Google Reviews 链接（强制 ⚠️ 二手参考）
- 一句话亮点

⚠️ 严格遵守用户口味边界。"不吃辣"就不能推泰式咖喱，哪怕是"招牌"。

报告控制在 1500 字内。
```

```
查询酒店 {酒店全名} 的设施信息。

- 泳池：户外/室内/有无儿童池/开放时间

来源优先级：
1. 酒店官方网站（best）
2. 该酒店在 Booking / Agoda 的设施列表

返回结构化 Markdown，每个字段一行。**查不到的字段写 unknown，不要猜**。
```

### 6. 机票比价

**何时跑**：A 阶段用户给出"机票未订"，可选 spawn。已订机票时改为"机票时间确认"轻量子任务（见下）。

**Prompt 模板**：

```
查 {出发地} → {目的地} 在 {YYYY-MM-DD} 出发、{YYYY-MM-DD} 返回的机票候选。
出行人数：{N 成人 + M 儿童}。

必须加载 web-access skill 并遵循其指引。

平台优先级：
1. Google Flights（https://www.google.com/travel/flights）— 全球航线综合
2. Skyscanner — 全球航线对比
3. 携程国际机票（出境）/ 携程（国内）— 中文用户主流
4. 去哪儿 / 飞猪 — 价格对比

**如果 network = cn-only**：跳过 #1 #2，直接用 #3 #4。在返回结果顶部标注：“⚠️ 国内模式，未对比 Google Flights / Skyscanner，价格可能比海外平台高 5-15%”，并提醒用户：“如果有海外网络，可以告诉我重新比价”。

注意：上述平台都有反爬，必须走 CDP 模式（web-access 提供）。短时间内打开过多新 tab 会被风控，控制节奏。

返回 5-8 个候选航班，每个含：
- 出发航司 + 航班号
- 出发/到达时间（含时区）
- 转机次数 + 转机点 + 转机时长
- 总飞行时长
- 票价（区分人均还是总价、是否含税、是否含行李）
- 退改签条款摘要
- 平台来源 + 直链

排序建议：先按总耗时分档，每档给 1-2 个不同价位的候选，让用户看清“便宜 vs 快”的取舍。

如果某段需要分开购票（联程被拆），明确指出风险（行李不直挂、误机不保护）。
```

### 7. 预约方式调研（可选）

**何时跑**：C 骨架定后或 D 餐饮定后，如果骨架内 ≥2 项需要预约（烹饪课、SPA、米其林餐厅、丛林飞跃、动物互动、包车一日等），询问用户：

> "你这个行程里有 X 项需要提前订（烹饪课、丛林飞跃、SPA…）。要不要我帮你查一下每项的预约渠道、提前期、价格区间？"

用户要才 spawn；不要默认。

**Prompt 模板**：

```
为以下旅行项目调研**实际可用的预约方式**。每项给 2-3 种渠道（推荐 → 备选）+ 提前期 + 中文用户实操要点 + 风险提示。

必须加载 web-access skill 并遵循其指引。当前 network = {global / cn-only}。

需要调研的项目：
1. {项目名 1}（DX 日期）
2. {项目名 2}（DX 日期）
...

每项给：
- 🥇 推荐渠道：Klook 中文版（适合 cn-only 模式）/ KKday / 携程 — 含中文界面、微信/支付宝、即时确认
- 🥈 官网/官方 IG/LINE 直订 — 通常便宜 5-10%，但可能要英文/邮件、收国际卡
- 🥉 邮件 / WhatsApp / 电话 / 酒店礼宾代订 — 兜底方案

每项还要包含：
- 提前期（"当天" / "1-2 天" / "3-5 天" / "5-7 天"）
- 是否需要预付定金 / 全款
- 是否含接送 / 含餐
- 孩子优惠条件 / 身高体重限制（特别是丛林飞跃、潜水）
- 营业时间 / 季节性关闭
- 联系方式（电话、邮箱、IG）

⚠️ 风险提示要明确：
- 国内卡能否过 3DS（很多东南亚商家国际卡才行）
- 该项目是否有"运营方变更"风险（如大象保育中心可能突然变饲养营）
- 是否有疫情后的政策变化未更新

⚠️ **不要硬塞具体的活动 URL**（如 klook.com/activity/12345）。子 agent 经常给"看起来对"但实际失效的 ID。**优先给搜索页 + 关键词形式**（如 `klook.com/search?keyword=清迈烹饪课`），让用户站内点选。如果给了具体 URL，必须本次跑过 curl 验证 200/301 才能写。

返回结构化 Markdown 表格：项目 | 提前期 | 渠道（按推荐度排序）。控制 1500 字内。

最后加一段"中文用户支付提示"：哪些渠道支持微信/支付宝、哪些要国际信用卡、3DS 验证容易卡的渠道。
```

### 6b. 机票时间确认（已订时的轻量子任务）

**何时跑**：用户在 A 阶段说"机票已订"且**没有提供起降时间**时。

不必 spawn 子 agent，直接由主流程问用户：

```
你提到机票已订，方便发我一下起飞和降落时间吗？比如：
- 去程：YYYY-MM-DD HH:MM 出发，HH:MM 落地
- 返程：YYYY-MM-DD HH:MM 出发，HH:MM 落地

不发也没关系，我会按"傍晚到、中午走"的常规假设排 D1/Dn，你看到不对再改。
```

用户给了就把时间写进 trip 数据结构，并基于此精确编排：
- D1 落地后剩余可用时间 = 22:00 - 落地时间 - 1.5h（出关 + 取行李 + 酒店路上）
  - >5h 可加 1 个轻活动（夜市 / 步行游 / 酒店附近吃饭）
  - 3-5h 仅 check-in + 酒店附近吃饭
  - <3h 直接酒店休息
- Dn 离开 = 出发时间 - 2.5h（国际航班）/ 1.5h（国内）回到机场
  - 反推退房时间和酒店最后一个活动的截止

## 并行 vs 串行执行

**并行（Claude Code 等支持 Agent 的环境）**：

- 在同一个回复内并发 spawn 签证子任务和速览子任务（B 断点前批次 1）
- 用户确认骨架方向后再 spawn 景点候选池（C 断点前批次 2）
- D 断点用户选择查机票后再 spawn 机票任务（批次 3）

每批次内的子任务并行，批次之间串行（前一批结果会影响后一批的 prompt 参数）。

**串行（Codex 等无 Agent 的环境）**：

完全相同的 prompt，按上述顺序一个一个执行。每个完成后把结果整理成结构化数据放到内存里，再开下一个。耗时显著拉长，但流程一致。

## 子任务结果聚合

子任务返回后，主流程负责：

1. **结构化校验**：每个字段是否齐了？缺的标 `unknown` 或追问用户
2. **冲突检测**：是否触发 B 断点（签证来不及/天气不适合/治安提醒）
3. **去重 + 合并**：景点候选池可能有重复，合并并保留最权威来源
4. **来源累计**：所有 URL 累加到主流程的“来源附录”里，最终写进 HTML 末尾

聚合后的数据结构（伪 JSON，便于内部传递）：

```json
{
  "trip": {
    "destination": "...",
    "origin": "...",

    "style": "...",
    "pace": "特种兵 | 紧凑 | 标准 | 度假 | 休养",
    "must_have": [...],

```
